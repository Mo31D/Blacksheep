# Storefront theme architecture

The existing versioned Website Appearance is the sole owner of theme choice, colours, hero content, section images and the optional `decorationsEnabled` switch. Presets remain in `commerce/src/data/website-appearance.ts`. Migration `0025_website_appearance_decorations.sql` gives historical versions a disabled switch, so an upgrade does not change the live storefront. The flag is copied into new drafts and restored versions; selecting Winter or Christmas in Admin suggests decoration, but saving a draft and publishing remain separate actions.

Flow: Admin Appearance editor → private preview/draft → explicit publish → D1 published Appearance version → `/v1/appearance` → `assets/commerce-live.js` → `syncWebsiteAppearance` in `assets/site.js`. Only a published Winter or Christmas version with decoration enabled loads `/assets/theme-layers.css`. The static storefront remains readable if the API or optional stylesheet is unavailable. The optional layer is removed when a later published version disables it. `theme-layers.css` is the single static owner of preset-scoped decorative rules and tracked assets; it must not fetch arbitrary Admin-supplied URLs.

The private Admin preview uses the same preset and switch from the draft response but does not change public state. Seasonal artwork and richer preview rendering belong to Slice 4. Slice 5 must verify bytes, mobile/reduced-motion behaviour and deployed staging acceptance. This source change does not migrate remote D1 or deploy either Worker or static site; migration and staging validation occur only in the release workflow. Production promotion requires explicit approval.
